Prototype: what a failed test prints

One run, two suites, four tests: search-person passes, no-token-is-rejected fails on the status code, create-user fails on a body value, and update-user is skipped because it needs create-user. Every variant keeps the log shape from docs/design/runs.md: a first line, one line per suite, the failures, a last line. The variants disagree on the failure text and on where the full request and response live.

The two suites in this mock (for the line numbers and the example body)

 2  kind: API

 5    headers:
 6      Authorization: Bearer ${{ secrets.production.api_token }}
 7

13      expect:
14        status: 200

17
18    - name: no-token-is-rejected
19      method: POST
20      path: /person/search
21      headers:
22        Authorization: null
23      expect:
24        status: 401

surface/api/users.yaml
 1  apiVersion: surface/v1
 2  kind: API
 3
 4  defaults:
 5    headers:
 6      Authorization: Bearer ${{ secrets.production.api_token }}
 7
 8  tests:
 9    - name: create-user
10      method: POST
11      path: /users
12      form:
13        email: u-${{ run.id }}@example.com
14        plan: free
15      expect:
16        status: 201
17        body: {"data": {"plan": "free", "status": "active"}}
18      save:
19        user_id: body.data.id
20
21    - name: update-user
22      needs: [create-user]
23      method: PATCH
24      path: /users/${{ needs.create-user.user_id }}
25      json:
26        note: "updated by ${{ run.id }}"
27      expect:
28        status: 200

Variant A: checks first, the exchange folded under them

What this variant decides
  • The failure text is a list of checks, one per line, each line <path>: expected X, got Y. Short.
  • Line one is a summary of the checks: it is the GitHub annotation.
  • The full request and response are in the log, folded in a ::group:: block under each failure. GitHub renders it closed. The reader clicks to open it.
  • A skipped test gets one line in the failures section, with the reason.

The two annotations the client writes (line one of each failure, with the test name in front):
::error file=surface/api/search.yaml,line=18::no-token-is-rejected: status: expected 401, got 200
::error file=surface/api/users.yaml,line=9::create-user: body: 2 differences from the example (match: values)

Variant B: a diff, like git

What this variant decides
  • The failure text is a unified diff: - is what the suite expects, + is what the target sent. The body diff shows only the keys the example has. Extra keys in the response pass, so they do not appear.
  • Line one is the first failed check. It is the GitHub annotation.
  • The response is the + side, so it is already in the log. Only the request is folded in a ::group::.
  • A skipped test prints nothing of its own. It is counted on the suite line and the last line.

Variant C: the response, with the checks beside it

What this variant decides
  • The failure text is the request, then the response pretty-printed, with ✓ and ✗ marks on the lines the checks looked at. Nothing is folded. The log is longer, and the reader scrolls instead of clicking.
  • Line one is a summary of the checks. It is the GitHub annotation.
  • A big response body is cut after 4 KiB with a line that says so. The whole body stays in the run result at GET /v1/runs/<id>.
  • A skipped test gets one line in the failures section, with the reason.
